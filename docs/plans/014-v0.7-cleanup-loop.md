# v0.7 cleanup loop

**Created:** 2026-05-10
**Branch:** `memex-v0.7`
**Purpose:** Get v0.7 to a tag-ready state via mechanical, non-architectural work. Designed to be executed as an iterative ralph-style loop (or by a fresh-context agent) with clear completion criteria.

## Requirements (decided 2026-05-10)

- **R1 — Audience:** memex is for the user across their own devices today (cross-device daemon model), eventually for other people too (memex is published). Implication: audit cleanup IS in scope; assume third-party readability when in doubt.
- **R2 — Offline behavior:** fail-closed. No local cache work. If it bites in practice, revisit.

These two requirements settle two of the four T2.x architectural questions. The remaining two (doc corpus location, daemon physical location) stay deferred — v0.7's current implementation is fine for now.

## Pre-decided judgment calls (so the loop doesn't stop)

- **AUD.M1 (homelab-named fixtures):** rename to generic placeholders (`host-a`/`host-b`, `Alex`/`Jordan` for personas, keep public model names like `Gemma`/`Qwen` as-is). Matches R1's "eventually shared" trajectory. *(deviating from this requires user input)*
- **AUD.M2 (pre-commit hook patterns):** move sensitive pattern list out of `.githooks/pre-commit` into a gitignored sidecar file the hook sources. Hook itself stays in repo and explains the indirection. Patterns themselves are the leak.

## Operating principle

Each item below is mechanically scoped: clear input, clear output, testable. **No item in this plan requires an architectural decision.** Decisions (T2.x in `013-post-v0.6.2-roadmap.md`) are explicitly out of scope.

The loop's job is to clean up; the user's job (separately) is to decide on architecture.

- **All Tier 2 architectural decisions** (`013` T2.1-T2.4): doc corpus location, daemon location, offline behavior, correction semantics. The loop ships v0.7 with the *current* implementation of each (single daemon, no cache, fail-closed implicit, dreaming-style corrections).
- **Tag `v0.7.0`** and trigger the publish workflow. User decides when to ship.
- **MemoryAgentBench eval** (T4.2). External benchmark, costs $.
- **FadeMem decay, RL ops, multimodal, causal grounding** (Tier 5). New features, not cleanup.
- **Branch operations**: don't merge to main, don't force-push, don't delete tags.
- **CI / release workflow changes** beyond what's needed to make tests/build pass.

If an item the loop is working on *requires* an architectural decision to proceed, **stop and surface the question** rather than guessing.

## Loop operating rules

Each iteration:

1. **Read this file** to find the next unchecked `[ ]` item.
2. **Do that item.** One commit per item is preferred; one commit per logical group is acceptable.
3. **Verify** before claiming done:
   - `npm test` passes.
   - `npm run build` succeeds.
   - `git diff` looks like what was intended.
   - Commit succeeds (don't bypass `--no-verify`; if pre-commit hook blocks, fix the underlying issue).
4. **Mark `[x]`** in this file in the same commit (or a follow-up commit) so the next iteration knows what's done.
5. **Push** to `origin/memex-v0.7`.
6. **End the iteration.** Don't try to do multiple items per iteration unless they're tightly coupled.

If an item is unclear or genuinely blocked:
- Mark it `[?]` (not `[x]`) in this file with a one-line explanation.
- Surface the blocker in the iteration log below.
- Move on to the next item.

If all items are checked OR explicitly marked `[?]` with rationale, output:
```
<promise>V0.7 CLEANUP LOOP COMPLETE</promise>
```

**Hard cap: 25 iterations.** If not done by then, the remaining items get surfaced as user-decision items.
