Where memex is

Memex has a strong retrieval system (94% E2E, rank-mode reranking, z-score fusion, confidence-gated skip). But it's a retrieval system, not a memory system.

The distinction
  • A retrieval system stores things and finds them.
  • A memory system stores, organizes, maintains, evolves, and intelligently surfaces knowledge.

What we learned from failures

Entity boost

BM25 already captures keyword matching. Adding entity overlap double-counted the same signal. Domain eval dropped from 80% to 73–75%.

Entity graph

3,406 links created. Zero quality impact. Correct memories weren't reachable from top hits via graph traversal.

Blend weight sweep

Raw-score blending dissolved reranker's ordinal signal. All weights failed until rank-mode scoring fixed the root cause.

"Don't implement what a paper describes — implement what makes their results different."
And: diagnose actual failures before scoping solutions.

The gap: five missing capabilities

1

Memory lifecycle

Memories are created and sit forever. No evolution, no consolidation, no reflection. Mechanical sweeps clean surface garbage but can't synthesize knowledge or detect contradictions.

2

Intake quality

Session import dumped 1,666 fragments using tiny sliding windows (3 turns, 500 char truncation). Research consensus: narrative chunking + frontier model extraction + two-phase dedupe. The extraction prompt is make-or-break (Mem0's defaults → 97.8% junk).

3

Pool hygiene

No semantic near-duplicate detection. No contradiction detection. No staleness detection. Deep sweep's age-based decay is too slow (90 days to reach 0.1).

4

Memory structure

Flat store with importance scores. No hierarchy, no typed networks, no temporal validity windows. Categories exist but don't influence retrieval.

5

Active observation

Auto-capture is passive — nudges the LLM to call memory_store. SOTA systems use background agents that actively observe and extract. Sliding-window capture code exists but is dormant.

Project 1

Pool cleanup

Remove the noise floor so every subsequent improvement has clean data to work with.

What
  • Aggressive decay for session imports: source=session + never-recalled + importance=0.3 → decay to 0.1 after 14d, evict after 30d
  • Semantic near-duplicate detection: cluster by embedding similarity, merge or delete
  • Manual audit of surviving high-importance memories for accuracy
Why first

Every other project builds on the pool. Reflection on garbage produces garbage insights. Better extraction into a noisy pool just adds more noise. Clean first.

Backing

Mem0 97.8% junk finding MemMachine 80% token reduction xMemory token efficiency

Measured by

Pool size reduction Domain eval stability Never-recalled ratio drop

Project 2

MCP Server

Memex as a standalone, always-on memory server. Cross-platform. Enables background processing.

What
  • MCP server over stdio — 5 tools (recall/store/forget/dream/stats)
  • Shared SQLite DB between OpenClaw plugin and MCP server
  • Background dreaming timer (reflection runs on schedule in server process)
  • Claude Code integration via .mcp.json
Why second — infrastructure, not a feature

The #1 gap with SOTA (Mastra, Letta) is no background processing. MCP server is a long-lived process that enables auto-dreaming, active conversation observation, and cross-platform memory (OpenClaw + Claude Code + Cursor). Also solves issue #8 (CLI hanging).

Backing

Mastra Observer+Reflector Letta sleep-time agents MCP universal agent integration

Measured by

Platforms ≥ 2 Background dreaming running Latency < 10ms overhead

Project 3

Dreaming reflection

LLM-driven knowledge synthesis — turn scattered facts into coherent learnings.

What
  • Stanford-style question synthesis: threshold trigger → generate questions → retrieve per question → synthesize insight → store as learning
  • Contradiction detection: find semantically similar memories, check temporal consistency, mark contradictions with superseded_by
  • Memory evolution: update stale memories with new context (A-MEM pattern)
  • Runs as part of MCP server's background dreaming cycle
Why third

After cleanup gives clean data and MCP server provides the runtime, reflection produces knowledge synthesis. The hierarchy emerges naturally from insights.

Backing

Stanford Generative Agents Graphiti bi-temporal contradiction A-MEM memory evolution Letta sleep-time validation

Measured by

Learnings generated Contradictions resolved Domain eval improvement

Project 4

Session import v2

Replace the garbage session import pipeline with LLM extraction that produces high-quality atomic facts.

What
  • Narrative chunking by topic boundaries (not fixed windows or bin-packing)
  • Frontier model extraction with custom prompt + few-shot examples + negative cases
  • Two-phase pipeline: extract → dedupe against existing store (Mem0 pattern, better prompt)
  • Provenance metadata (sessionKey, agentId, source)
  • Fact precision/recall measurement against human-labeled gold set
Why fourth

After cleanup and reflection establish what "good memory" looks like, the extraction pipeline has clear quality targets. Reflection provides contradiction detection for newly extracted facts.

Backing

Hindsight narrative chunking Mem0 two-phase pipeline Letta hybrid approach

Measured by

Precision no hallucinated facts Recall no missed facts Pool quality after re-import

Project 5

Model bakeoff

Evaluate whether newer models improve retrieval without architectural changes.

What
  • EmbeddingGemma-300M — 10x smaller, MRL dimension truncation
  • Contextual AI Reranker v2 — instruction-following, +35% recency-awareness
  • Run through existing bakeoff harness (domain eval + fast benchmark + E2E)
Why fifth

Model improvements are incremental. Architecture improvements (projects 1–4) have higher leverage. Once data is clean, better models provide additional gains.

Measured by

Domain eval LongMemEval R@1/R@3/E2E Latency

Project 6

Memory hierarchy

Evolve from flat store to structured knowledge — topic → episode → fact.

What
  • Reflection naturally produces higher-level memories (learnings, insights)
  • Cluster by topic, generate topic summaries
  • Coarse-to-fine retrieval: match topics first, drill into facts (HyperMem)
  • Uncertainty-gated expansion: abstracts first, detail on demand (xMemory)
Why last

Hierarchy emerges from reflection and clean data. Building hierarchy on a noisy flat store would be premature structure.

Backing

HyperMem hypergraph xMemory 4-level hierarchy MACLA 15:1 compression
